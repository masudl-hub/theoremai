# v0.3.2

## Summary

You can now serve a host profile's tools to MCP clients, such as coding agents and chat apps, from one endpoint. A model that is too busy for a call now fails with its own error kind, `busy`, and the kernel moves the call to the fallback key slot.

## What's New

- **Serve a host profile over MCP.** `createTheoremMcpHandler` from `@theoremjs/react/server` serves the tools of a host profile over MCP Streamable HTTP. Its options type is `TheoremMcpHandlerOptions`. Mount the handler on one route. It takes `POST` only and keeps no session between requests.

  ```ts
  import { createTheoremMcpHandler } from '@theoremjs/react/server';

  export const mcp = createTheoremMcpHandler({ profile: docsTools, version: '1.0.0' }); // mount at /mcp
  ```

  - Clients of the `2026-07-28` revision send their version and capabilities on each request. The handler answers `server/discover`, `tools/list`, and `tools/call` for them.
  - Clients that open with `initialize` (revisions `2025-11-25`, `2025-06-18`, and `2025-03-26`) also get answers. The handler answers `initialize`, `ping`, `tools/list`, and `tools/call` for them.
  - `tools/list` gives each tool the profile allows, with its input schema. A tool's `access` becomes the MCP hints: `read-only` sets `readOnlyHint`, and `destructive` sets `destructiveHint`.
  - For clients of the `2026-07-28` revision, the `server/discover` result may be cached for one hour (`ttlMs: 3600000`). The `tools/list` result may be cached for 5 minutes (`ttlMs: 300000`). Both results have `cacheScope: 'public'`, because neither result holds data about the caller.
  - `tools/call` runs the tool through the gates, the guardrails, and the trace of the kernel. The client gets the text that a model would read, not the raw output. A tool that fails returns a result with `isError: true`.
  - No one can approve a call over MCP. When the handler is created, it throws if an allowed tool has a permission other than `auto`.
  - The handler refuses a request from a browser page on another origin with status 403. To allow an origin, add it to `origins`.

- **A `busy` error kind.** `ERROR_KINDS` and `ErrorKind` from `@theoremjs/agents` now include `busy`. A provider that answers with HTTP 503 or 529 is up but too busy for the call. That failure is now `busy`, not `unavailable`. A close of a `geminiLive` session with code 1013 is also `busy`.
  - If a fallback key slot is set and the vault holds its key, the kernel tries that slot once after a `busy` failure. This happens only before the first event. Before, it did this only after a `rate_limit` failure.
  - If the profile's `autoContinue` lists the stop, a text turn can send a `busy` call again.
  - The user reads the label `error.busy`: "Sorry, the model is busy right now. Please try again in a moment."
  - The host route answers a `busy` failure with status 503.

- **`quotaBusy`.** `quotaBusy` from `@theoremjs/agents` (also from `@theoremjs/agents/guardrails`) gives the error for a client whose last turn is still running, that is, when `takeSlot` returns `busy`. The error has the kind `rate_limit`. The user reads the label `quota.busy`: "Sorry, your last message is still being answered. Please wait for it to finish."

## What's Fixed

- **A 529 response was not sent again.** Before, Theorem did not send a request again after HTTP 529 (overloaded), and the failure was `unavailable`. Now a model call, and a `read-only` HTTP tool, is sent again after a 529, on the same waits and limits as a 503. A 529 that remains is `busy`.
- **A failed send was retried or not by its message.** Before, Theorem read the error message of a send that got no response. It sent the request again only when the message held words such as "fetch failed" or "ECONNRESET". A failure with other words was not sent again. Now one rule decides: a send that got no response, and was not aborted or timed out, is a network error. Theorem sends it again and never reads its message.

## Breaking Changes

- **`ErrorKind` has a new member, `busy`.** This affects code that covers each kind, such as a `Record<ErrorKind, …>` or an exhaustive `switch`. That code does not type-check until you add `busy`.

  ```ts
  // 0.3.1
  const retryable: Record<ErrorKind, boolean> = { /* … */ unavailable: true /* … */ };

  // 0.3.2
  const retryable: Record<ErrorKind, boolean> = { /* … */ busy: true, unavailable: true /* … */ };
  ```

- **HTTP 503 and 529 are now `busy`, not `unavailable`.** This affects a host or UI that reads `errorKind`, and a trace dashboard that reads `error.type`. A close of a `geminiLive` session with code 1013 also changes from `unavailable` to `busy`. `kindOfHttpStatus` from `@theoremjs/agents/guardrails` now returns `busy` for 503 and 529. Where you match `unavailable`, match `busy` too.
- **Custom wording for `error.unavailable` does not cover a busy model.** If your profile's `labels` replace `error.unavailable`, the user now reads the default `error.busy` text for a 503 or 529. To keep your wording, also set `error.busy`.

## Notes

- `@theoremjs/agents`, `@theoremjs/react`, and `@theoremjs/studio` ship in lockstep. Upgrade all three to 0.3.2 together.
- `@theoremjs/studio` has no change in behavior in this release.
- A `decision` profile's error does not change. A `busy` failure gives the decision error code `unavailable`, as a 503 did before.
- The host route status for a 503 does not change: `busy` and `unavailable` both answer with 503.
- An MCP client of the `2026-07-28` revision that sends `ping` gets the JSON-RPC error "Method not found". Clients that open with `initialize` get an empty result for `ping`.
