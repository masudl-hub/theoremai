# v0.3.5

## Summary

A background call's result reaches the turn that is running when the call ends, and your app decides who tells the model, and when a chat wakes for it. A tool says which of its media the person sees, and a stage can give a failed call details or end the turn.

## What's New

- **The model can cite a line of a live call by id.** Pass `lines` to `runSession` with three functions: `reserve` gives an id, `note` words what tells the model the id, and `keep` takes each finished line. A user line ends when the model acts on it, and the model's line is its whole turn. The model reads a user line's id before that line, so it can cite the line it is hearing. A tool call reaches the host only after the line before it is kept. With or without `lines`, the session history now holds one entry per line. Before, it held one entry for each piece of transcription.
- **An app's own record of late tool calls reaches its web handler and the studio.** `TurnWiring.prepare` can return `execution` and `background`. The web handler runs them with the session's own: the app's coordinator decides each call, and the session records the same call, so the page still shows it and its late end. Before, the handler dropped both, so a studio turn's late call never reached the app's store. The studio's chat now has a notifier, so an open chat redraws when a late call ends.
- **A host hears a step's events while `runToolStep` settles it.** `runToolStep` takes `onEvent`, which is given each of the step's events as it arrives, before the call it belongs to is yielded. A host can pass a call's `progress` on to a page while the step runs and still read each call's end. Before, a host had to pick: `invokeToolStep` gave the events and left settling each call to the host, and `runToolStep` gave each call's end only once it settled. `ToolStreamEvent`, what a streaming handler yields, is exported.
- **A host that settles a call itself frames the failure as the kernel does.** `formatToolFailureForModel` is exported. A live session whose tool runs in another process that cannot answer settles the call with its own `error` event; write its `readBack` with `formatToolResult(formatToolFailureForModel(failure))`, and the model reads the same `Tool error (code): …` words as for every other failure. See [stages.md](../contracts/stages.md).
- **A tool call can end the turn.** A `post_tool` handler on a text turn can return `end: true`. Every call of the step settles, then the turn ends as `completed` with the reply the model wrote before its calls, which can be empty. The model takes no further step, and `before_end` does not run. The reply still passes its checks; a refused reply is retried like any other. Before, the only way to stop after a call was `abort`, which ends the turn as `cancelled`. See [stages.md](../contracts/stages.md#end).
- **A step's tool calls can give the model new context for its next step.** A new stage, `post_step`, runs on a text turn once every call of a step has settled, before the model's next step. `ctx.settledCalls` lists the step's calls in the model's order, each `completed` or `failed`. Its handler can return `context: { server }`, which replaces the host's context in the turn's opening message, so the next step reads it. It passes the same checks as the request's context, and the guardrails at the context boundary. A `post_step` `stage` event with `contextReplaced: true` says it landed. With `tools.parallel: true`, a context built there sees what every call of the step wrote. A call that replies before its body ends is settled at its reply. Before, the context was read once per turn, so a model step after a save still read what was true before it. See [stages.md](../contracts/stages.md#context).
- **A called agent runs on the path you name.** `onAgentCall` can return `path`, as it returns `model`. Without one, the called agent's turn has no path, so it gets only the tools on every path (`'*'`).
- **A called agent's `when` lines read the options you name.** `onAgentCall` can return `options`, which fill the called profile's own `identity.options`. The caller's options are not passed down, so without them no `when … is …:` line fits.
- **A label can tell shapes apart by their leading field.** A `when` takes `has`: `'when action has erase: erasing an item'` fits when the model sent `{ action: { erase: … } }`. Before, a `when` compared only text, a number, or true or false, so a tool whose input is one of several keyed shapes could not word each one. `registerTool` refuses a `has` on a field that is not a group, or one that names a field the group never holds, and names the fields it has. A prompt line's `when` refuses `has`, since an option is one value.
- **A `post_tool` stage can add details to a failed call.** Before, a failed call could only be denied: `mutate` was a `mutate_invalid` warning there, so a host could not give the model the id of the record it kept for the call. Now `mutate: { details }` on a failed call replaces `failure.details` and keeps the code, the kind, and the message. The guardrails read the new details first. The model's read-back, the `error` event, the stored outcome and the trace carry them. `{ output }` still rewrites a completed call. `{ details }` on a completed call, `{ output }` on a failed one, or `details` that is not a JSON object is a `mutate_invalid` warning.
- **A `deny` can carry details.** `deny: { code, message, details }` at `pre_tool` or `post_tool` puts `details`, a JSON object, on the failure, the same as `mutate: { details }` does. Before, a call refused at `post_tool` settled with no details, so a host whose finish step failed after the tool returned could not give the model the id of what it kept. Details that are not a JSON object are a `deny_invalid` warning, and the call is still refused, without them.
- **A tool says which media the person sees.** A media part in a tool's `parts` takes `sent: true` when the person should see it as well as the model. Without `sent`, only the model reads it. A tool can also return a reference, `{ type, mimeType, uri }`, such as a `gs://` object: the person sees it and the model never reads it, so a private address never reaches a provider. `toolOutputPartSchema` and `ToolOutputPart` describe these parts, and the `complete` tool event carries them. An MCP tool's image or audio block whose `annotations.audience` includes `"user"` is sent, and a `resource_link` with a `mimeType` becomes a reference. An agent tool sends the media its agent made.
- **A tool's media part carries your own values, and a bad part fails the call.** A bytes part or a reference takes `metadata`, such as a caption or a length. Theorem does not read it, and the model never sees it. The `complete` event, the chat's media block, and the reference that `resolveMedia` gets carry it as you gave it. A part with a field it does not name, empty bytes, a blank `mimeType`, or an empty `uri` now fails the call as `invalid_output`, with the bad field named. Before, the kernel dropped the field or the part, and nothing said so. A `post_tool` `mutate` that replaces the output is checked the same way.
- **Guards read a tool's parts.** The text parts the model reads are read at `tool_output_<kind>` with the result. Each part the `complete` event carries is read at `tool_shown_<kind>`, every field but a file's bytes. A part blocked there is left out, and the other parts stay. Before, no guard read the parts.
- **Guards read the text files a tool returns.** A CSV, plain-text, or Markdown part in a tool's `parts` is decoded and read at `tool_output_<kind>` and at `tool_shown_<kind>`, the same way an attachment is. Where the person sees it, the file is read in the `complete` event's `output` and in its `parts`. The model reads the file as UTF-8, with a CSV's formula cells escaped. The person gets the file's own bytes, and a redact writes the new text back in the file's own encoding. A tool that is not exposed to the model (`exposeToModel: false`) is not read at `tool_output_<kind>`, since the model reads none of it. Before, a tool's file bytes passed unread, so a file a person attached was read and the same file from a tool was not. A text file whose `data` is not base64 now fails the call as `invalid_output`.
- **The page decides which tool media to show and how to load a reference.** `TheoremChat` takes `media`: `'sent'` (the default) shows only what a tool sent, and `'all'` also shows what only the model read. `resolveMedia` turns a reference into an address the page can load, under the viewer's own sign-in. Until it answers, and when it gives none, the chat shows the file name. `TheoremHost` and the direct-run console take the same `resolveMedia`. The studio shows all tool media and loads `http(s)` references as they are.
- **Pictures and videos open in your own viewer.** `TheoremChat`, `TheoremHost`, `LiveRunner`, and `TheoremSurface` take `mediaViewer`, a component given the items, the one shown, and whether it is open. The transcript's pictures and galleries, a tool's images and data, a decision's marked box, and a form field's image all open in it. An item names the saved file it came from as `reference` when there is one. Without `mediaViewer`, each opens Astryx's Lightbox, with zoom, as before. `useMediaViewer` opens the page's viewer from your own component. See the [React README](../../react/README.md#your-own-media-viewer).
- **A call shows its tools' media as a chat does.** `LiveRunner` takes `media` and `resolveMedia`, as `TheoremChat` does. Its captions show the media a tool sent, or every piece with `media="all"`, and a reference through `resolveMedia`. Before, a call had neither prop, so it never showed what a tool returned for the model alone, and a reference showed only as a file name. The studio's call shows all of a call's media, as its chat does.
- **Your app decides who tells the model that a background call ended.** Set `lateResultsDecider` on your `TurnWiring`. Theorem runs the replies; the decider's `policy` picks the results the model reads at each moment, and keeps its own count, such as a cap or quiet hours. `moment.host` says whose chat it is. It is asked as a reply opens, after each step, once the model has answered, and as the reply ends. `ended` hears each call end, with `wake` to reply from the server and `notify` to tell the open pages. Unset, nothing tells the model: no page wakes the chat, and no reply reads a late result. `tellEveryResult` from `@theoremjs/web/server` tells every result to the first reply that runs, lets the open page wake the chat, and gives up a result after two replies read it without telling it. The studio reads the same decider from your entry.
- **One reply at a time reads a chat, and a result is told once its reply is saved.** The new entrypoint `@theoremjs/agents/conversation` runs each reply under a hold of the conversation (`runConversation`). The app gives the storage (`ConversationInbox`) and the policy. A reply that fails gives its results back, with a record of the reply that had them, so a later reply reads them. A result that ends as a reply saves keeps the hold, and a follow-up tells it. `@theoremjs/agents/conversation/testing` has the scenarios every inbox must pass. The web handler keeps its inbox in the session store, and `conversationLeaseMs` sets the hold's lease.
- **A server with no page request runs the handler's replies.** `createTheoremConversationCore` from `@theoremjs/web/server` runs a message, an answer, a wake, a read, a rewind, a steer, and a stop with a run context, `{ sessionId, signal, host? }`, where `createTheoremHandler` reads the `Request`. Each run returns how it ended: `released`, `continue` with its `hold`, `held` with `leasedUntil`, or `lost`. After a `continue`, call `followUp` for the next reply or `release` to let the conversation go; `followedUp` does either for you. `createTheoremHandler` takes `onContinue`, which says whether the handler runs the next reply in the same response or your app runs it. Pass `inbox` to hold the conversation in your own `ConversationInbox`, under your own policy. Your `prepare` receives the reply's hold as a second argument, with the items the reply reads. Pass `saved` with a message your app saved in its own write, and the core posts nothing. `createTheoremHandler` runs on the same core, and behaves as before. See the [web README](../../web/README.md#run-replies-with-no-page-request).
- **A chat wakes when its background calls end.** When the policy tells a result to a reply to no message, the conversation read says `wake: true`, and an idle page posts `<base>/wake`. The handler runs that reply under a hold, so two pages that wake at once run one reply. A wake that fails gives its results back, and the chat wakes again. A message sent during a wake takes the chat, and the wake writes nothing. A server wake that finds another reply running tries again once that reply's lease runs out. In `ChatTranscript`, the wake's reply continues the turn, and a trace the person opened stays open.
- **A live call reads what waits for it, and the host can make the model answer with no one speaking.** `SessionRequest.lateResults` takes the same `LateResultsSource` a text turn takes. A call asks it as each turn opens, after each call settles, and once the model has answered, and each landing is a `late_results` event. `LiveSession.wake()` makes the model read what waits and answer. While the model answers or one of its calls is open, the wake folds into that turn's next moment (`folded`, with the `stage`). Otherwise a turn starts (`started`), or nothing landed and the model says nothing (`nothing_landed`). Each `stage` event of a turn a wake started carries the wake's id. Before, a call read an `onStage` inject only when someone spoke, and never read a late result. See [kernel.md](../contracts/kernel.md#waking-a-live-call).
- **A late result lands in the turn that is running when it ends.** `TurnRequest.lateResults` is a function, a `LateResultsSource`. A text turn asks it as it opens, after each step whose calls settled, and once the model has answered. What it gives lands as one message that the model reads on its next step, and the reply counts it as a read. Giving the same call's result again adds no second message. A `TurnWiring.prepare` can return its own source, which runs with the session's: the app's results come first. A source that throws is a `hook_failed` event with `hook: 'lateResults'`, and the turn goes on.
- **A stage handler can return several named injects.** A stage result takes `injects`, a list of `{ id, messages }`, in place of `inject` and `injectId`. They land together, in the order given, and `stage.injected` names each one with the messages it added. Before, a handler could name one inject per stage, so a host with two things to tell had to merge them under one id and could not say which of them the model read. An entry with a blank or repeated id, or `injects` together with `inject`, refuses them all with a warning. See [stages.md](../contracts/stages.md).
- **Your app shapes the save that ends a reply.** `createTheoremConversationCore` takes `beforeSave`, `afterSave`, and `compact`. `beforeSave` receives how the reply ended and the blocks the save adds, and returns the blocks to write, the inbox items the save marks as told, and a value of its own for the store. The store's `write` receives them in a fifth argument, a `WriteContext`, with the reply's hold, so a store on a database can write the reply, mark the items, and check the hold in one statement. `afterSave` runs after the write, while the run still holds the conversation. `compact` replaces the core's own compaction. A reply to a message whose hold a newer message took over is given to `beforeSave` and to `write` with `ended: 'lost'` and nothing told; the memory store and the sealed store refuse that write. With none of these options, a reply saves as before. See the [web README](../../web/README.md#shape-the-save-that-ends-a-reply).
- **The web handler takes your app's inbox and your steps around a save.** `createTheoremHandler` takes `inbox`, `beforeSave`, `afterSave`, and `compact`, as `createTheoremConversationCore` does. A reply that the page starts then runs under a hold of your conversation, and a wake tells the items that wait in your inbox. The type `ReplyWiring` names these options and `prepare`. The handler now asks `host` one time for a request. Your store marks the items in `told` in its `write`. When it does not, the run fails with a `config` error instead of telling the same items in follow-up after follow-up.
- **Your app can save each page message before a reply runs.** `createTheoremHandler` takes `intake`, your own save of a message from `/turn` or `/steer`. It needs `inbox`. `intake` returns a `MessageIntake`: `opened` with the hold your write took, and the handler runs the reply under it, or `saved`, when another reply holds the conversation and reads the message from your inbox. A steer is then an item in your inbox, not an inject into the running turn. The chat keeps a saved message in its pending list, marked Sent, until a reply reads it. The core has `checkMessage`, which refuses a bad message before your save. `ComposerPendingMessage` has `saved`, and `@theoremjs/agents/interface` exports `saveComposerPendingMessage` and `takeSavedComposerPending`. A `conversation` line can carry `landsAs` and `opened`. See the [web README](../../web/README.md#save-a-pages-message-in-your-own-write).
- **A stop reaches the reply that holds the conversation.** Before, a stop reached a turn only by the page's `turnId`, in `steerInbox`, so a reply that a channel, a wake or a follow-up ran could not be stopped. Now your `inbox` can carry `stop`, a `HoldStop`: `ask` records a stop for the hold that has the conversation, `stopped` tells the reply under that hold, and `clear` removes the stop as the reply ends. `<base>/stop` and the core's `stop` then call `ask` and do not read `turnId`. A stop is for one reply, so the follow-up under the same hold runs. Unset, a stop works as before.
- **Your app can refuse a reply with a line of its own.** `prepare` on `createTheoremConversationCore` and on `createTheoremHandler` can return `{ refuse: { text, host? } }` in place of the turn. No model runs. The line is the reply, and the reply saves with `ended: 'refused'`, with no error block and no usage. While your app would refuse, its inbox `policy` tells only the items that the refusal answers. The type is `ReplyRefusal`.
- **A transcript block and a named inject can carry your app's own values.** Set `host`, a JSON object, on a block that `beforeSave` returns or on an `injects` entry. The stage event's `injected` entry and each block made from the inject carry it. Theorem never reads it. A page cannot set it: a restored transcript and a start request lose it. A `host` on an inject that is not a JSON object refuses the stage's injects with an `inject_host_invalid` warning.
- **A page on your app's inbox hears each reply your app saves.** With `inbox` and `notifier` set, the conversation read always offers `notify`, so the open page keeps `POST <base>/notify` open. Call `publish` with the session id after your app saves a reply away from the page, such as a reply to another channel or a reply your sweep runs, and the page reads the chat again. Before, the page listened only while a background call ran, so it showed such a reply only on its next turn or reload. With no `inbox`, the page listens only while a call runs, as before.
- **A wake goes on after a gate that nobody answered.** With `gateTtlMs` set, a wake that finds a paused reply with every gate past its limit cancels those calls as expired and then runs, in one save. While a gate can still be answered, the wake returns `held` with the time the last gate lapses, and runs nothing. Before, a paused reply stopped every wake until the person sent a message. With `gateTtlMs` unset, a gate never lapses and a wake runs nothing, as before. See the [web README](../../web/README.md#share-session-authority).
- **An inject can bring the tools it asks the model to use.** A stage result takes `promote`, a list of tool ids, with its `inject`. When the inject lands, each T2 tool among the turn's gated tools goes on the model's list, as from `tools.t1Policy`. Before, a turn kept the tools it opened with, so an inject that asked for a tool the turn had not opened with could not be acted on. A bad `promote`, or one without an `inject`, warns `inject_promote_invalid`. See [stages.md](../contracts/stages.md).
- **A write after a remote read can ask the person.** `guardrails.taint.afterRemoteRead` takes `{ write, destructive }`, each `'off'`, `'confirm'` or `'block'`. `'confirm'` holds the call for the user's approval, and an approval runs it. One approval answers the taint ask, a `remoteDestination` ask and `always_confirm` together, on one card. A `pre_tool` stage reads the turn's record as `ctx.taint`, so you can write your own rule. See [guardrails.md](../contracts/guardrails.md).
- **Check a credential before you keep it.** `probeTool` sends one request to an HTTP or MCP tool's service the way the tool's own call sends it: the credential where `auth` puts it, through the network guardrail, redirects followed with the credential kept to the first origin, and an MCP server asked for its tool list in a session when it asks for one. It returns `accepted`, `refused` (a 401 or 403 to the credential), `inconclusive` with a reason (any other answer, such as 402 or 500), or `unanswered` with a reason. The answer's body comes back with the credential omitted, and nothing is stored. A host can say "connected" only when the service took the key. The studio's connection test now runs on it, so it follows redirects and opens an MCP session as a call does, and it reads the whole body unless the tool sets `maxResponseBytes`. Before, it stopped at a redirect, could not reach a server that needs a session, and cut a body at 1 MB without saying so. See [kernel.md](../contracts/kernel.md).
- **Keep tool keys out of the run.** Pass a `SealedCredentialSource` as `credentials`, and the run never reads a key: it asks the sealed side to ready a slot, and sends each request on the call's own origin through it. Build that side with `sealedCredentialHost({ source, slots })` in a process the run's code cannot reach, such as its own Worker, and give the run a source that forwards `prepare` and `send` to it. Each slot names the `resource` its key may go to; a request anywhere else is refused before the key is read. An expiring OAuth token is refreshed and stored on the sealed side. Gates, refusals, scopes and echoes work as with a source the run reads. A key typed at a sign-in gate is refused under a sealed source: the person enters it where the keys are kept. A sealed side that throws fails only that call, reported as `hook_failed` with `hook: 'credentials'`.
- **A reply can show its steps where they came.** `ChatTranscript` and `TheoremChatTranscript` take `stepLayout`. `'trace'`, the default, folds the reply's thoughts and tool calls, with the words between them, under its work status, as before. `'inline'` keeps each where it came: every word in the open, calls side by side as one row, and each thought a folded "Thought: …" line. `showToolDurations={false}` leaves out how long each call ran, and `showWorkStatus={false}` leaves out the reply's "Worked for 3.5s" (a reply whose steps fold under it keeps "Worked" to open them).
- **A page shows a reply that runs elsewhere.** A page that opens while a reply runs, after a reload, in another tab, or while another channel's reply runs, used to show nothing until it ended: the message was gone and so was the working state. Your store's `read` now returns `running: { since, prompt, heldUntil }` on the `ConversationSnapshot` while a reply runs under a hold you keep. `ConversationView.running` brings it to the page, and `ChatState.runningElsewhere` (and so `useTheoremChat`'s) holds it. The page acts as it does for its own reply. The phase is `streaming`, the working pill counts from `since`, and what the person said shows under the transcript. Stop, steer, queue and send now work. `/stop` and `/steer` take `{ conversation }` in place of `turnId` for the reply that holds the conversation, and the core's `stop` takes either. A host that has no `inbox` stop, or no `intake` for a steer, refuses those with the new `session.reply_unreachable`, not `session.turn_ended`, because the reply may still run. The queue sends on when your `notifier.publish` says the reply ended, and the page reads again at `heldUntil` if it has heard nothing by then.
- **OAuth calls take a time limit.** Every OAuth call (`discoverResourceMetadata`, `discoverAuthServerMetadata`, `createOAuthPkceFlow`, `exchangeOAuthPkce`, `refreshOAuthToken`, `revokeOAuthToken`) and `sealedCredentialHost` take `timeoutMs`: how long each request to the authorization server may take, its body read included. Past it the call throws a `TimeoutError` (kind `timeout`). Without it there is no limit, as before.
- **The composer can sit on one row.** `TheoremChat` takes `composerLayout="row"`, and `ChatComposerBar` takes `layout="row"`. The field, the mic and send share one line, and text that wraps moves the field onto its own line until the draft is empty. Above the composer, a pill shows the reply in progress with its stop button, and a pill shows each background call until its result lands. While a reply runs or a step waits, Enter queues a draft and send opens the send menu. `'stacked'`, today's composer, stays the default. `useTheoremChat` returns `backgroundJobs`, and `backgroundJobs(blocks)` gives the same list from a transcript. The studio sets the layout in Settings, under Chat. The working pill reads "Working for 12s" on the same clock as the transcript's status line. What waits to send sits in a tray of its own above the row, which folds to one line. Every part of the row's look is a `--theorem-composer-*` CSS property, `TheoremChat` takes `composerIcons` for its glyphs, and its words are labels.
- **You can place the composer and the transcript apart.** `@theoremjs/react/ui` exports `TheoremChatComposer` and `TheoremChatTranscript`, each bound to the `chat` from `useTheoremChat`. `TheoremChat` is built from the same two pieces. The host decides where each one sits and when each one shows, and Theorem moves neither. `useTheoremChat` returns `shownBlocks`, `turnClock` and `workingSince`, so both pieces show the same time. `ChatTranscript` takes `clock`. `TheoremSurface` gives the pieces the theme, labels and media settings that `TheoremChat` takes.
- **The chat names the gate that waits for the person.** `ChatState.waitingGate`, and so `useTheoremChat`'s `waitingGate`, is the confirmation, permission or sign-in gate the reply waits on, and `null` when none waits. A page gate is never one: the page answers it.
- **The send menu shows each item's shortcut, and steer and send now have one.** In both layouts, Queue shows ↵, Steer this reply ⌘↵, Send now ⌘⇧↵, and Stash ⌘⇧S (Ctrl on Windows and Linux). While a step waits for approval, Queue says it sends once you answer the step, and Send now says it cancels the step. `composerShortcut(event)` from `@theoremjs/web/client` names the menu action a keydown asks for, and `COMPOSER_SHORTCUTS` gives each action's key.
- **A profile can limit how long a message is.** Set `inputs.maxTextChars` on a `text` or `image` profile. The kernel refuses a longer `input.text` before the model runs. The reason is the `text.too_long` label: `Sorry, that message is too long. Please keep it under {maxTextChars} characters.` The check runs when a turn starts, with files or without. A message of exactly the limit passes. It counts `.length`, like an HTML `maxlength`, on the text as the agent receives it, after the page's redaction. `resolveTurn` refuses a longer message too. `steer` on the conversation core refuses a steer over the limit, and now takes `{ turnId, id, input }`. `TheoremChat` runs the same check before it sends, on the same redacted text. The message stays in the composer, and the notice clears when the text changes. The studio has a Limit length switch, a Max characters field, and a Text area for the label. `AttachmentValidationCode` has `text_too_long`, and `validateProfileInputs` takes the draft's `text`. Unset, there is no limit. See [kernel.md](../contracts/kernel.md).
- **A profile can keep its tool calls' data from the people in the chat.** Set `tools.showData: false` on a `text` or `image` profile. The web handler then sends the page no call's input or output: not in a reply's events, a conversation read, or a rewind. A request's `arguments` is `{}`, a completed call's `output` is `null`, and the call's draft, progress, trace steps and late results are not sent. Media a tool sent the person, and references, still reach them. Each call shows only its labelled row, with its status and how long it took, and a failed call still shows its message. An approval shows its request and asks with no input, and the call runs with the input the model gave. The saved transcript keeps the data, so the model's history is whole. The interface carries the setting as `tools.showData`. `TheoremChat` and `TheoremChatTranscript` read it, and `ChatTranscript` takes `showToolData` for the same choice. Unset, the people in the chat can read both, as before. A server of your own applies the same rule with `eventWithoutToolData` and `blockWithoutToolData` from `@theoremjs/agents/interface`.
- **A store can check one block.** `@theoremjs/web/server` exports `transcriptBlockSchema`, the check `storedConversationSchema` runs on each transcript block. Use it when your store keeps blocks one at a time, in a row or a column, and not as one stored conversation.
- **A failed call that wrote part of its reply is sent again, and you pick what becomes of its words.** A text profile whose `autoContinue` names `provider_error` or `stream_incomplete` sets `turnBehaviour.resumption.partialReply`. `'retract'` takes the words back, with the sources they cited, and sends the call again as it was: the model writes its reply from the start. `'continue'` keeps the words and their sources: the model reads them, with the new `resume.partial_reply` note that its call failed there, and goes on from where they stop. A call that showed a structured reply or its draft, or a file, is taken back whole in either mode. Each re-send is a new `resend` event whose `reply` says what became of what the failed call showed: `'retracted'` takes back every reply event it showed, and `keptReply`, `foldTurnEvents`, `appendAssistantEventsToHistory` and an agent tool's output leave them out; `'continued'` kept its words; `'unshown'` means it showed nothing. A `'continued'` resend carries `notice`, the profile's `resume.reply_continued` words ("This reply was interrupted and picked up where it left off."), which `foldTurnEvents` keeps as a `resumed` block and `ChatTranscript` draws in the reply's status row, beside its time; `showResumedNotice={false}` leaves it out. Studio shows the choice as "Failed call's words" when Auto sends a failed call again. Before, a call that had shown any of its reply was not sent again, and the turn ended with its failure.
- **Every page open on a conversation draws a running reply live.** Pass `replyFeed`, with `notifier`, to `createTheoremHandler` or `createTheoremConversationCore`. A reply writes each line to your `TheoremReplyFeed`, and the open pages read `follow: true` in the conversation read and post `POST <base>/follow`. They draw the steps, the pill and the words from the reply's first line, whoever started it: another page, a wake, a follow-up, or your app with no page request. `createMemoryReplyFeed` keeps one process's replies, with no size limit. Before, a page that did not start a reply saw only the working state, and read the reply once it ended. See the [web README](../../web/README.md#follow-a-running-reply).
- **A steer and a stop reach a reply through its conversation inbox, with no store of your own.** Without `inbox`, Theorem keeps its own inbox for each conversation, and a steer is a message in it, beside the ended background calls. The reply takes it at `pre_turn`, `post_tool` or `before_end`, and a save of the reply that took it tells it once. A chat that keeps no conversation is named by its run: the `turnId` the page sent. A stop reaches the reply that holds the conversation, by `{ conversation }` or by the page's `turnId`. Both live in process memory, so a steer must reach the process that runs the reply. The wire and the page do not change. See the [web README](../../web/README.md#steer-and-stop-without-your-own-inbox).

## What's Fixed

- **A person's saved file stays on their side of the chat.** Before, a `user-attachment` or `user-voice` block held only bytes. To show a file it had saved, an app used a `media` block, and the chat put that block in the next reply, as if the model had sent it. Now these blocks take `uri` and `type` in place of `data`, and `metadata` for your own values, and the chat shows the file through `resolveMedia`: a picture, a voice note to play, or the file name. A reference in a person's injected message keeps its `uri` and `type` too. Before, it showed only its MIME type.
- **The composer takes a pasted or dropped file.** Before, the text field ignored a file pasted into it or dropped on it: a drop did nothing and a pasted picture was lost. Now, when the profile takes attachments, a pasted or dropped file goes to the same tray as a file from the attach button, under the same limits. The send still checks each file's type.
- **The types of `@theoremjs/react` resolve in your project.** `TheoremChatState`, `LiveCall` and `useImageReader` were declared through paths outside the package, so their fields were `any`. They are now declared from the public entries, and the build fails if a declaration reaches outside the package.
- **A text attachment is read in its own encoding.** Before, an attachment was read as UTF-8, or as windows-1252 when it was not valid UTF-8. A byte order mark and the type's `charset` were not used. So a UTF-16 file was read wrong, and a key in it was not found. The model then got UTF-8 bytes under the old `charset`. Now the guard reads the file by its byte order mark, then by its `charset`, and the model gets UTF-8 under `charset=utf-8`.
- **The guardrails read a failed call's details.** Before, they read a failure's message at `tool_failure_<kind>` but not its `details`, so a key or an injection in the details reached the model and the `error` event. Now the details are read at the same boundary, as a result's data is at `tool_output_<kind>`. This holds for details the handler states in a `ToolFailed` and for details a `post_tool` stage sets. A redacted match is replaced in what the model reads back. Blocked details settle the call as `output_blocked`, as a blocked result does. The `error` event's details are now read at `tool_shown_<kind>` too.
- **A host lists its agent tools.** Before, `hostInterface` left out every tool of type `agent`, so `<TheoremHost />`, the studio's host console, and `createTheoremMcpHandler` did not show one the host allowed, though a call to it ran. Now they list it with the input its caller fills, and `HOST_TOOL_KINDS` includes `agent`.
- **A reply that writes and calls a tool is one message.** Before, history held the words a model step wrote and the calls it made as two assistant messages. The model read its words as a reply already finished, and often wrote them again after the call. Now the step is one assistant message with `content`, `tool_calls`, and the reasoning, as every provider takes it. This holds in turn history, a provider checkpoint, `appendAssistantEventsToHistory`, `historyFromTranscriptBlocks`, and a live session when its text arrives before the call. When an inject drops the words a step wrote before its calls, the calls stay in the message without them.
- **A late result no longer clears a reply's taint.** Before, a late result that landed as a paused reply went on was read as the start of a new reply, so a run after the next approval lost what the reply had read before it. Now a late result that lands inside a reply is part of it, and the marks last to the end of the reply.
- **A background call keeps its end in the saved reply.** Before, a saved reply kept the call as it detached, and a read of the chat took its end from the session. Once the session dropped the settled operation, the reply showed the call as lost. Now the end is saved on the call's step when the call ends, and again after any reply write, so a reload shows the call done with what it read for as long as the reply is kept. The step keeps `detached` (`at`, and `readBack` when the model read a running note), so history still replays what the model read as the call detached. A call saved before this release keeps its background step until it ends again or the session drops it. If your app keeps a call's end itself, save it on the step with your store's `end` and `detachedEnding(operationId, outcome, { clientEvents, labels })` from `@theoremjs/web/server`, which gives the end as the page reads it.
- **A failed call shows the person's wording, not the model's message.** Before, a failed tool row in `ChatTranscript` showed `failure.message`, which is what the model read, such as an upstream error. A background call's end read late, or saved on its step, also had no `failure.error`, because the chat read it without the profile's labels. Now every event the chat reads, saves or reads late carries the profile's wording first, a failed call saved without that wording gets it when the conversation is read, the row shows `failure.error`, and the message shows only in the call's details.
- **A background call whose end the session lost is still told.** Before, the model never read a call the session marked `uncertain`, or one whose settled operation it dropped (after `operationRetentionMs`, or to fit `maxStateBytes`), and `ended` did not hear it. Now the model reads that the action is unresolved, once, and `ended` hears it. A result given up stays given up after the session drops it.
- **A message or a rewind sent as a wake saves goes on after the wake's reply.** Before, a message or a rewind that read the chat while a wake was saving its reply failed with a conflict. Now the message posts after the reply the wake saved, and the rewind cuts that reply away with the rest. When that reply stopped on an approval, both fail with `session.gate_pending`, and the approval waits.
- **A tool request form reads `anyOf`.** Before, an input that picks one of several shapes, or that may be null, showed as one JSON box, and its sample was the word `example`. Now a choice of shapes shows as a picker. Each option is named by its one key, its tag's value, or its `title`, and picking one shows that shape's fields. The sample starts on the first shape. A field that may be null shows its fields and a **Send null** switch, so leaving a field out and sending null stay two different requests. `missingFields` and `sampleFromSchema` follow the shape you picked. `chosenBranch`, `branchValue`, `inBranch`, `branchField` and `branchSample` read the shapes for a form of your own, and a field has `isNullable` when null is one of its options. The labels are `@theorem.decision.send_null` and `@theorem.decision.shape`.
- **The studio opens a project whose tools set `after`.** It read each tool's input with the `after` field the kernel added, and registering it again added the field a second time, so the project did not compile. It now reads the input the tool declared, with `declaredInputSchema` from `@theoremjs/agents/kernel`, and a replay keeps the tool's `after`. A registered tool that sets `after` also registers again as it is: the kernel keeps the `after` field it added instead of refusing it, so the studio can register a tool the builder edited. A tool's own field named `after` is still refused. A host profile, its MCP tool list and the studio's request form show such a tool with the input it declared, without `after`: a call from the page or an MCP client is one call, with no other call in its step to wait for.
- **The model reads that `after` takes tool names.** The `after` field told the model to name tools, but not that a call id is refused, and a model sent one. The `tool.after_field` label now says the field takes the names of other tools called in the same step, not call ids. A call whose `after` names only tools with no other call in the step still fails `wait_unknown`, and the model now reads the new `tool.after_unknown` label, which says `after` takes tool names, so it can correct the call. A `waitFor` that names a call not in the step still reads `tool.wait_unknown`.
- **A file the provider cannot read no longer takes the other files with it.** Before, when the provider refused one file, the call went again without every file of the turn, so the model lost files it could read. Gemini names the type it refused, for example `text/plain` sent as a document or `image/x-icon`. OpenRouter names the kind a model has no endpoint for, as `image/*`, `audio/*` or `video/*`, and an upstream that cannot decode a clip refuses `audio/*`. Now the call goes again without only the files of that type or kind, wherever the conversation holds them, and the model reads every other file. A file a tool returned gets the new label `turn.media_refused_tool`. A provider names one type per refusal, so each refused type costs one more call. If the call still fails, the named files stay out and `done.mediaRefused` still names them. The `error` event has the new field `refusedMedia`. A refusal that names no type goes on as before. As before, this needs `autoContinue` to list `provider_error`.
- **A profile takes every type its `accept` list names.** Before, the kernel refused a file whose type was not in `MEDIA_INPUT_KINDS`, even when the profile accepted it, for example `image/svg+xml` under `image/*`, or a Word file. The turn ended with an `input` error. Now a type the kernel does not name takes the kind of its top-level type: an `image/`, `audio/` or `video/` type is that kind, and any other type is a document. Only a string that is not a MIME type is still refused, and the person now reads the same reason as for any type the profile does not take. A file the provider cannot read is dropped, and the turn goes on.
- **An HTTP or MCP tool with `exposeToModel: false` is hidden from the model.** Before, only a function tool or an agent tool hid its result, and an HTTP or MCP tool gave the model its whole output and its pictures. Now every tool reads the flag the same way. The model reads only `Completed.` (the `tool.completed_hidden` label), no picture the tool names is fetched for the model, and the person still sees what the tool sends and its references. A hidden tool that is not signed in still tells the model so under `onUnauthenticated: 'report_to_model'`, since those words are the kernel's, not the tool's. A saved call of a hidden HTTP or MCP tool replays only `Completed.`, as a function tool's does.
- **A credential echoed URL-encoded is omitted too.** Before, a service that repeated a key URL-encoded (in a redirect's `Location`, or in a text answer) sent it back to the run as it was. Now the sender omits it in each form a service may echo it in: as sent, escaped in a JSON string, and URL-encoded (either hex case, or form-encoded).
- **What lands at a live call's `before_end` gets a turn of its own.** Before, the cycle ended as the inject was sent, so the model's answer to it ran with no `pre_turn`, no `before_end` and no `post_turn`. Now the next turn opens as that cycle ends.
- **A live inject a guardrail blocks is not reported as landed.** Before, a stage inject whose text the inbound check blocked was still in the stage's `injected` list, so a host marked the item told when the model never read it. Now a live call reads injects at the `injected` boundary, as a turn does. A block sends none of the stage's injects, `injected` names none, and the call goes on.
- **A live `system` inject reaches the model as host words.** Before, a live call sent every inject inside the `<user_data>` fence, so the model read the host's words as the person's. Now a `system` inject goes outside the fence and history keeps it as a system message. A `user` inject is still fenced.
- **A credential source that throws fails one call, not the turn.** Before, a host source whose `get`, `set` or `clientSecret` threw as a tool signed in ended the turn. Now the call fails as not started, with `failure.code: 'hook_failed'`, and a `hook_failed` event names `hook: 'credentials'` and the call. This includes a `clientSecret` that throws, which before settled as `refresh_failed`. A refused refresh's `detail` no longer holds the tokens or client secret it was sent.
- **Studio keeps a continue-by-itself list the file leaves out.** A profile file with no `autoContinue`, opened in Studio and saved, got the kernel's default list, so the profile began to continue cut replies and send failed calls again by itself. Now Studio writes `autoContinue` only when you pick it.
- **A retried reply takes its sources with it.** After an `attempt` (validation or egress), `keptReply` and every reader built on it drop the `citation` events of the reply thrown away, as they drop its text. Before, the thrown-away reply's sources stayed on the reply that replaced it.
- **A called agent's drafts stop when its reply is taken back.** An agent tool's call stops sending `draft` phases at a `resend` that withdraws what the agent showed, as it does at an `attempt`, and its output is the reply the agent kept.
- **A line the page has been given counts as delivered in the next stage.** The reply's lines went to the page through a queue that took each line and returned at once, so the run, the inbox offer and `afterWrite` ran ahead of the page. A host that read what the person already has mid-reply, such as a count of delivered lines, saw queued lines as undelivered and planned the rest as if the person had nothing. Now each line is handed on only when the page has taken it and its handling is done, and the next stage waits for that. A slow page slows the reply by its own pace.

## Breaking Changes

- **`operationRetentionMs` has no default.** `createTheoremHandler` and `createTheoremSessionBoundary` now require it. `DEFAULT_OPERATION_RETENTION_MS` is removed from `@theoremjs/web/server`. Theorem sets no number for how long a finished call is kept: pass the time your app keeps it.

  ```ts
  createTheoremHandler({ profile, operationRetentionMs: 24 * 60 * 60 * 1000 });
  ```

- **A conversation store has `end`.** `TheoremConversationStore` requires `end(sessionId, ending)`, which saves a background call's end on its step in the saved reply. Apply it with `endedBlock` from `@theoremjs/web/server`, and do not change the revision. A store that cannot write one step, such as a sealed store, can do nothing. With `authorizeToolReplay`, the chat calls no `end`, and a read takes the end from the session, where your check runs.

- **`ReplyEnd` has the value `refused`.** A store or a `beforeSave` that reads `ended` by case must handle it. A `ReplyRunner` of your own can set `refused` to save a reply in this way.
- **A gate that nobody answered in time tells the model so.** A call cancelled with the resume cause `expired` and no sign-in now fails with the code `expired` and the new label `session.gate_lapsed`. Before, it failed with the code `cancelled` and the label `session.abandon_gated`, which says the person sent a new message. A session's released call that nobody answers reads the same way. `lapsedGateFailure` takes the cause as its second argument: `lapsedGateFailure(tool, 'expired', service, labels)`.
- **`allowModelSelect` and `allowEffortSelect` are about the interface only.** The kernel now runs any model and effort the profile declares, whether these are on or not; a name the profile does not declare is still refused. Your server code, such as the web handler's `prepare`, can choose the model per turn. The page's own pick is refused unless the profile lets the interface pick it: the web handler, the embedding handler and the live session boundary check it with `refuseInterfacePick` from `@theoremjs/agents/interface`. If you call `runTurn` or `runSession` yourself with a model the page sent, call `refuseInterfacePick(profile, { model, effort })` first.

  ```ts
  createTheoremHandler({
    profile, // allowModelSelect: false, models: { fast, smart }
    prepare: (turn) => ({ ...turn, model: (turn.input.text ?? '').length > 2000 ? 'smart' : 'fast' }),
  });
  ```

- **`prepareLiveOpen` and `liveSessionOpen` take the profile.** The call checks the page's model and effort against it. Pass the profile the call opens on as the second argument; server context moves to the third.

  ```ts
  // Before
  await boundary.prepareLiveOpen(open, hostContext);
  // After
  await boundary.prepareLiveOpen(open, profile, hostContext);
  ```

- **`ToolCredentialSource` needs `delete(slot)`.** It forgets the slot's credential, as when the person disconnects a service, and after it resolves `get(slot)` answers `undefined`. Call it after `revokeOAuthToken`. The kernel never calls it. A source you wrote fails to type-check until you add it; `memoryCredentialSource` and the web handler's session source have it.

  ```ts
  const userCredentials: ToolCredentialSource = {
    get: (slot) => vault.load(userId, slot),
    set: (slot, credential) => vault.save(userId, slot, credential),
    delete: (slot) => vault.remove(userId, slot),
  };
  ```

- **A bad tool media part fails the call.** Before, the kernel skipped a part it could not read and dropped fields a part does not name. Now the call fails as `invalid_output`. Put your own values in `metadata`. `coerceToolResultParts` is gone; check parts with `toolOutputPartSchema`. `projectForModel` throws when the output's parts were not checked.

- **`input.lateResults` is gone.** Give late results from `TurnRequest.lateResults`, a function the turn asks at each moment it can read them. A stored held turn whose input has `lateResults` no longer parses.

  ```ts
  // Before
  runTurn({ profile, input: { text, lateResults: outcomes } }, model);
  // After
  runTurn(
    { profile, input: { text }, lateResults: ({ stage }) => (stage === 'pre_turn' ? outcomes : []) },
    model,
  );
  ```
- **The `late_results` event and the `late-results` block say which calls they hold and where they landed.** The event carries `operationIds`, `stage`, `step` and `inReply`, and the block carries `operationIds` and `inReply`. A stored transcript whose `late-results` block has no `operationIds` or `inReply` no longer parses. Each outcome needs its call's `operationId`. The kernel knows it read a result by that id, not by its text, so a second call that returned the same text is read too.
- **A stream handler can no longer yield `artifact`.** The `{ kind: 'artifact' }` handler event, the tool phase `artifact` and `ToolCall.artifacts` are gone. Nothing showed them. A tool's media goes in its output `parts`. The chat shows a part marked `sent: true`, and a reference, beside the result. A stored transcript or trace that holds an `artifact` phase no longer parses.
- **Provider wire helpers moved from `@theoremjs/agents/kernel` to `@theoremjs/agents/providers`.** `turnStopFromOpenAiFinishReason`, `turnStopFromInteractionStatus`, `wireInteractionPart`, `CACHE_MODES`, `CACHE_TTLS`, `CacheSpec`, `CacheMode` and `CacheTtl` now ship beside the protocols that use them. Import them from `@theoremjs/agents/providers`; the package root still exports them. Nothing they do changed, and `options.cache` on an `openRouterOpenAi` model works as before.
- **`StageApplyWarningCode` has a new member.** It now includes `'inject_promote_invalid'`. A `switch` that must cover every code fails to type-check until you add this case.
- **`StageApplyInput.mutable` is now `mutates`.** It names what `mutate` rewrites at the fire: `'input'`, `'output'` or `'details'` (`StageMutateSubject`). Left out, there is nothing to rewrite, and `mutate` is a `mutate_invalid` warning. Before, `mutable` left out meant `mutate` applied. If you call `applyStageResult` yourself, pass `mutates` where `mutate` may apply.
- **The `images` hook is now `media`.** `media(output)` returns entries, not strings: `{ url }` to fetch a picture for the model, `{ url, sent: true }` to show it to the person too, or a reference `{ type, mimeType, uri }` that is shown and never fetched. Change `images: (o) => o.urls` to `media: (o) => o.urls.map((url) => ({ url }))`.
- **Image URLs in a tool's output no longer become media.** The page no longer finds image addresses in a tool's output and shows them. `collectPromotedMediaFromToolOutput`, `promotedMediaFromUrlString` and `PromotedToolMedia` are gone, and a `media` transcript block has no `url` or `previewUrl`. A tool block's media now holds `data` or a reference `uri`, and `fromTool` and `sent` say where it came from. A stored transcript whose `media` block holds `url` no longer parses. The direct-run panel no longer shows the image links in a call's output either: `layoutResult` returns no `images`, and `returnedMedia` takes only the call's parts. To show a picture, return it in `parts` with `sent: true`, or return a reference.
- **The chat shows only the tool media a tool sent.** Before, `TheoremChat` showed every media part of a tool's `parts`. Now, by default (`media="sent"`), it shows only the parts marked `sent: true` and the references. Mark the parts the person should see with `sent: true`, or pass `media="all"` to show every part.
- **The MCP handler sends only what a model reads.** `tools/call` on a `createTheoremMcpHandler` handler returns the text and media a model reads. It leaves out the references a tool returned, and all the media of a hidden tool, whose `complete` event now says `hidden: true`.
- **`guardrails.taint.afterRemoteRead` is an object.** It was `'off'`, `'destructive'` or `'write'`. Now it takes `{ write, destructive }`, and each is `'off'`, `'confirm'` or `'block'`. Left out, `destructive` is the same as `write`, and `defineProfile` refuses a `destructive` weaker than `write`. `remoteDestination` takes `'off'`, `'confirm'` or `'block'` as before, now typed `TaintGate`. `DESTINATION_GATES`, `DestinationGate` and `DestinationVerdict` are gone. `checkTaintGate` takes the object and returns a `TaintVerdict`, `{ verdict, confirm? }`. The studio's `LentKeys` `holds.afterRemoteRead` takes the same object.

  ```ts
  // Before
  guardrails: { taint: { afterRemoteRead: 'destructive' } }
  // After
  guardrails: { taint: { afterRemoteRead: { destructive: 'block' } } }
  // Before: 'write'
  guardrails: { taint: { afterRemoteRead: { write: 'block' } } }
  ```
- **`resolveToolAuth` answers with a sender, not a secret.** It returns `{ auth: 'none' }`, `{ auth: 'signed_in', signedIn: { send, credentialId, audience?, omit? } }`, `{ auth: 'failed', failure }` when the credential source threw (the call fails as not started, and a `hook_failed` event names `hook: 'credentials'`), or the gate, model message or failure as before. `send` is a fetch that places the credential on one hop, never follows a redirect, and replaces the credential wherever the service echoes it. Read `signedIn !== undefined` where you read the secret before. `credentials` on a turn, a tool call and `ToolContext` is now a `CredentialSource`: narrow it with `isSealedSource` before you call `get` or `set`.

- **A live inject takes only `user` and `system` messages, read at `injected`.** An inject with an `assistant` or `tool` message, or with parts, is now refused whole (`inject_invalid_messages`); before, its text was sent as the person's words. A live inject is no longer read at the `live_user` boundary: set the `injected` boundary to guard it.

- **A `/steer` body carries the draft, not an inject.** `TheoremSteerRequest` is now `{ turnId, id, input, conversation? }`: `id` is the steer's id and `input` is the message, as `/turn` takes it. Before, the body was `{ turnId, inject }`, and the page built the inject. The handler now builds it. `transport.steer` resolves with a `TheoremSteerReply`, `{ saved? }`; a transport of your own returns `{}` unless your host saves steers itself. `onUserBlocks` in a run session receives a second argument, `own`.

- **`TheoremStopRequest` and `TheoremSteerRequest` are unions, and the core's `stop` takes the stop request.** A stop is `{ turnId }` or `{ conversation }`. A steer is `{ turnId, id, input, conversation? }` or `{ id, input, conversation }`. Code that reads `.turnId` on either must check `'turnId' in request` first. The core's `stop(at, { turnId })` is now `stop(at, request)`, and it throws `session.reply_unreachable` for `{ conversation }` when your `inbox` has no `stop`. `ChatState` has the new field `runningElsewhere`: a `ChatState` you build in a test or a fake must set it, to `null` when no reply runs elsewhere.

  ```ts
  // Before
  const id = request.turnId;
  // After
  const id = 'turnId' in request ? request.turnId : undefined;
  ```

- **A page no longer repeats a wake that ran nothing.** After a wake that fails, that the person stops, or that streams no line, the page waits for the next conversation read before it wakes again. Before, it posted `/wake` again at once while the read said `wake: true`.

- **`isStashShortcut` and `STASH_SHORTCUT` are gone from `@theoremjs/web/client`.** Use `composerShortcut(event) === 'stash'` and `COMPOSER_SHORTCUTS.stash`.

- **A text profile that sends failed calls again says what becomes of their words.** `defineProfile` refuses a text profile whose `autoContinue` names `provider_error` or `stream_incomplete` without `turnBehaviour.resumption.partialReply`. A profile that leaves `autoContinue` out sends nothing again, and needs no change.

  ```ts
  // Before
  resumption: { autoContinue: ['provider_error'] }
  // After
  resumption: { autoContinue: ['provider_error'], partialReply: 'retract' }
  ```

- **`TurnEvent` has a new type, `resend`.** A switch that names every event type needs a case for it. Read a reply with `keptReply(events)` so the words a re-send took back are left out.

- **The steer inbox is gone.** Removed from `@theoremjs/web/server`: `SteerInbox`, `SteerUnit`, `createMemorySteerInbox`, `steerStage`, `steerUnitOf` and `stopOnRequest`, and the `steerInbox` option of `createTheoremHandler` and `createTheoremConversationCore`. A steer goes through the conversation inbox. The core's `steer(at, args)` takes `{ ref, id, input }` or `{ turnId, id, input }`, and throws a `config` error when you set `inbox`: set `intake` and the handler saves the steer into your inbox. A stop with no `stop` in your `inbox` reaches Theorem's own stop for a reply this process runs, and throws `session.reply_unreachable` for a reply the store says runs elsewhere. New: `personMessageOf`, `createOwnInbox`, `openRun`, `steerRun`, `scopedStop`, `namedRun`. The studio draft handler's `steer` option is now `own`. A steer sent after the reply ended is refused with `session.turn_ended`.
