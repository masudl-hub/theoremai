# v0.3.5

## Summary

A background call's result reaches the turn that is running when the call ends, and your app decides who tells the model, and when a chat wakes for it. A tool says which of its media the person sees, and a stage can give a failed call details or end the turn.

## What's New

- **The model can cite a line of a live call by id.** Pass `lines` to `runSession` with three functions: `reserve` gives an id, `note` words what tells the model the id, and `keep` takes each finished line. A user line ends when the model acts on it, and the model's line is its whole turn. The model reads a user line's id before that line, so it can cite the line it is hearing. A tool call reaches the host only after the line before it is kept. With or without `lines`, the session history now holds one entry per line. Before, it held one entry for each piece of transcription.
- **An app's own record of late tool calls reaches its web handler and the studio.** `TurnWiring.prepare` can return `execution` and `background`. The web handler runs them with the session's own: the app's coordinator decides each call, and the session records the same call, so the page still shows it and its late end. Before, the handler dropped both, so a studio turn's late call never reached the app's store. The studio's chat now has a notifier, so an open chat redraws when a late call ends.
- **A host that settles a call itself frames the failure as the kernel does.** `formatToolFailureForModel` is exported. A live session whose tool runs in another process that cannot answer settles the call with its own `error` event; write its `readBack` with `formatToolResult(formatToolFailureForModel(failure))`, and the model reads the same `Tool error (code): …` words as for every other failure. See [stages.md](../contracts/stages.md).
- **A tool call can end the turn.** A `post_tool` handler on a text turn can return `end: true`. Every call of the step settles, then the turn ends as `completed` with the reply the model wrote before its calls, which can be empty. The model takes no further step, and `before_end` does not run. The reply still passes its checks; a refused reply is retried like any other. Before, the only way to stop after a call was `abort`, which ends the turn as `cancelled`. See [stages.md](../contracts/stages.md#end).
- **A called agent runs on the path you name.** `onAgentCall` can return `path`, as it returns `model`. Without one, the called agent's turn has no path, so it gets only the tools on every path (`'*'`).
- **A called agent's `when` lines read the options you name.** `onAgentCall` can return `options`, which fill the called profile's own `identity.options`. The caller's options are not passed down, so without them no `when … is …:` line fits.
- **A label can tell shapes apart by their leading field.** A `when` takes `has`: `'when action has erase: erasing an item'` fits when the model sent `{ action: { erase: … } }`. Before, a `when` compared only text, a number, or true or false, so a tool whose input is one of several keyed shapes could not word each one. `registerTool` refuses a `has` on a field that is not a group, or one that names a field the group never holds, and names the fields it has. A prompt line's `when` refuses `has`, since an option is one value.
- **A `post_tool` stage can add details to a failed call.** Before, a failed call could only be denied: `mutate` was a `mutate_invalid` warning there, so a host could not give the model the id of the record it kept for the call. Now `mutate: { details }` on a failed call replaces `failure.details` and keeps the code, the kind, and the message. The guardrails read the new details first. The model's read-back, the `error` event, the stored outcome and the trace carry them. `{ output }` still rewrites a completed call. `{ details }` on a completed call, `{ output }` on a failed one, or `details` that is not a JSON object is a `mutate_invalid` warning.
- **A `deny` can carry details.** `deny: { code, message, details }` at `pre_tool` or `post_tool` puts `details`, a JSON object, on the failure, the same as `mutate: { details }` does. Before, a call refused at `post_tool` settled with no details, so a host whose finish step failed after the tool returned could not give the model the id of what it kept. Details that are not a JSON object are a `deny_invalid` warning, and the call is still refused, without them.
- **A tool says which media the person sees.** A media part in a tool's `parts` takes `sent: true` when the person should see it as well as the model. Without `sent`, only the model reads it. A tool can also return a reference, `{ type, mimeType, uri }`, such as a `gs://` object: the person sees it and the model never reads it, so a private address never reaches a provider. `toolOutputPartSchema` and `ToolOutputPart` describe these parts, and the `complete` tool event carries them. An MCP tool's image or audio block whose `annotations.audience` includes `"user"` is sent, and a `resource_link` with a `mimeType` becomes a reference. An agent tool sends the media its agent made.
- **A tool's media part carries your own values, and a bad part fails the call.** A bytes part or a reference takes `metadata`, such as a caption or a length. Theorem does not read it, and the model never sees it. The `complete` event, the chat's media block, and the reference that `resolveMedia` gets carry it as you gave it. A part with a field it does not name, empty bytes, a blank `mimeType`, or an empty `uri` now fails the call as `invalid_output`, with the bad field named. Before, the kernel dropped the field or the part, and nothing said so. A `post_tool` `mutate` that replaces the output is checked the same way.
- **Guards read a tool's parts.** The text parts the model reads are read at `tool_output_<kind>` with the result. Each part the `complete` event carries is read at `tool_shown_<kind>`, every field but a file's bytes. A part blocked there is left out, and the other parts stay. Before, no guard read the parts.
- **The page decides which tool media to show and how to load a reference.** `TheoremChat` takes `media`: `'sent'` (the default) shows only what a tool sent, and `'all'` also shows what only the model read. `resolveMedia` turns a reference into an address the page can load, under the viewer's own sign-in. Until it answers, and when it gives none, the chat shows the file name. `TheoremHost` and the direct-run console take the same `resolveMedia`. The studio shows all tool media and loads `http(s)` references as they are.
- **A call shows its tools' media as a chat does.** `LiveRunner` takes `media` and `resolveMedia`, as `TheoremChat` does. Its captions show the media a tool sent, or every piece with `media="all"`, and a reference through `resolveMedia`. Before, a call had neither prop, so it never showed what a tool returned for the model alone, and a reference showed only as a file name. The studio's call shows all of a call's media, as its chat does.
- **Your app decides who tells the model that a background call ended.** Set `lateResultsDecider` on your `TurnWiring`. Theorem runs the replies; the decider's `policy` picks the results the model reads at each moment, and keeps its own count, such as a cap or quiet hours. `moment.host` says whose chat it is. It is asked as a reply opens, after each step, once the model has answered, and as the reply ends. `ended` hears each call end, with `wake` to reply from the server and `notify` to tell the open pages. Unset, nothing tells the model: no page wakes the chat, and no reply reads a late result. `tellEveryResult` from `@theoremjs/web/server` tells every result to the first reply that runs, lets the open page wake the chat, and gives up a result after two replies read it without telling it. The studio reads the same decider from your entry.
- **One reply at a time reads a chat, and a result is told once its reply is saved.** The new entrypoint `@theoremjs/agents/conversation` runs each reply under a hold of the conversation (`runConversation`). The app gives the storage (`ConversationInbox`) and the policy. A reply that fails gives its results back, with a record of the reply that had them, so a later reply reads them. A result that ends as a reply saves keeps the hold, and a follow-up tells it. `@theoremjs/agents/conversation/testing` has the scenarios every inbox must pass. The web handler keeps its inbox in the session store, and `conversationLeaseMs` sets the hold's lease.
- **A chat wakes when its background calls end.** When the policy tells a result to a reply to no message, the conversation read says `wake: true`, and an idle page posts `<base>/wake`. The handler runs that reply under a hold, so two pages that wake at once run one reply. A wake that fails gives its results back, and the chat wakes again. A message sent during a wake takes the chat, and the wake writes nothing. A server wake that finds another reply running tries again once that reply's lease runs out. In `ChatTranscript`, the wake's reply continues the turn, and a trace the person opened stays open.
- **A late result lands in the turn that is running when it ends.** `TurnRequest.lateResults` is a function, a `LateResultsSource`. A text turn asks it as it opens, after each step whose calls settled, and once the model has answered. What it gives lands as one message that the model reads on its next step, and the reply counts it as a read. Giving the same call's result again adds no second message. A `TurnWiring.prepare` can return its own source, which runs with the session's: the app's results come first. A source that throws is a `hook_failed` event with `hook: 'lateResults'`, and the turn goes on.
- **An inject can bring the tools it asks the model to use.** A stage result takes `promote`, a list of tool ids, with its `inject`. When the inject lands, each T2 tool among the turn's gated tools goes on the model's list, as from `tools.t1Policy`. Before, a turn kept the tools it opened with, so an inject that asked for a tool the turn had not opened with could not be acted on. A bad `promote`, or one without an `inject`, warns `inject_promote_invalid`. See [stages.md](../contracts/stages.md).

## What's Fixed

- **The guardrails read a failed call's details.** Before, they read a failure's message at `tool_failure_<kind>` but not its `details`, so a key or an injection in the details reached the model and the `error` event. Now the details are read at the same boundary, as a result's data is at `tool_output_<kind>`. This holds for details the handler states in a `ToolFailed` and for details a `post_tool` stage sets. A redacted match is replaced in what the model reads back. Blocked details settle the call as `output_blocked`, as a blocked result does. The `error` event's details are now read at `tool_shown_<kind>` too.
- **A host lists its agent tools.** Before, `hostInterface` left out every tool of type `agent`, so `<TheoremHost />`, the studio's host console, and `createTheoremMcpHandler` did not show one the host allowed, though a call to it ran. Now they list it with the input its caller fills, and `HOST_TOOL_KINDS` includes `agent`.
- **A reply that writes and calls a tool is one message.** Before, history held the words a model step wrote and the calls it made as two assistant messages. The model read its words as a reply already finished, and often wrote them again after the call. Now the step is one assistant message with `content`, `tool_calls`, and the reasoning, as every provider takes it. This holds in turn history, a provider checkpoint, `appendAssistantEventsToHistory`, `historyFromTranscriptBlocks`, and a live session when its text arrives before the call. When an inject drops the words a step wrote before its calls, the calls stay in the message without them.
- **A late result no longer clears a reply's taint.** Before, a late result that landed as a paused reply went on was read as the start of a new reply, so a run after the next approval lost what the reply had read before it. Now a late result that lands inside a reply is part of it, and the marks last to the end of the reply.
- **A background call whose end the session lost is still told.** Before, the model never read a call the session marked `uncertain`, or one whose settled operation it dropped (after `operationRetentionMs`, or to fit `maxStateBytes`), and `ended` did not hear it. Now the model reads that the action is unresolved, once, and `ended` hears it. A result given up stays given up after the session drops it.
- **A message or a rewind sent as a wake saves goes on after the wake's reply.** Before, a message or a rewind that read the chat while a wake was saving its reply failed with a conflict. Now the message posts after the reply the wake saved, and the rewind cuts that reply away with the rest. When that reply stopped on an approval, both fail with `session.gate_pending`, and the approval waits.

## Breaking Changes

- **A bad tool media part fails the call.** Before, the kernel skipped a part it could not read and dropped fields a part does not name. Now the call fails as `invalid_output`. Put your own values in `metadata`. `coerceToolResultParts` is gone; check parts with `toolOutputPartSchema`. `projectForModel` throws when the output's parts were not checked.

- **`input.lateResults` is gone.** Give late results from `TurnRequest.lateResults`, a function the turn asks at each moment it can read them. A stored held turn whose input has `lateResults` no longer parses.

  ```ts
  // Before
  runTurn({ profile, input: { text, lateResults: outcomes } }, model);
  // After
  runTurn(
    { profile, input: { text }, lateResults: ({ stage }) => (stage === 'pre_turn' ? outcomes : []) },
    model,
  );
  ```
- **The `late_results` event and the `late-results` block say which calls they hold and where they landed.** The event carries `operationIds`, `stage`, `step` and `inReply`, and the block carries `operationIds` and `inReply`. A stored transcript whose `late-results` block has no `operationIds` or `inReply` no longer parses. Each outcome needs its call's `operationId`. The kernel knows it read a result by that id, not by its text, so a second call that returned the same text is read too.
- **A stream handler can no longer yield `artifact`.** The `{ kind: 'artifact' }` handler event, the tool phase `artifact` and `ToolCall.artifacts` are gone. Nothing showed them. A tool's media goes in its output `parts`. The chat shows a part marked `sent: true`, and a reference, beside the result. A stored transcript or trace that holds an `artifact` phase no longer parses.
- **Provider wire helpers moved from `@theoremjs/agents/kernel` to `@theoremjs/agents/providers`.** `turnStopFromOpenAiFinishReason`, `turnStopFromInteractionStatus`, `wireInteractionPart`, `CACHE_MODES`, `CACHE_TTLS`, `CacheSpec`, `CacheMode` and `CacheTtl` now ship beside the protocols that use them. Import them from `@theoremjs/agents/providers`; the package root still exports them. Nothing they do changed, and `options.cache` on an `openRouterOpenAi` model works as before.
- **`StageApplyWarningCode` has a new member.** It now includes `'inject_promote_invalid'`. A `switch` that must cover every code fails to type-check until you add this case.
- **`StageApplyInput.mutable` is now `mutates`.** It names what `mutate` rewrites at the fire: `'input'`, `'output'` or `'details'` (`StageMutateSubject`). Left out, there is nothing to rewrite, and `mutate` is a `mutate_invalid` warning. Before, `mutable` left out meant `mutate` applied. If you call `applyStageResult` yourself, pass `mutates` where `mutate` may apply.
- **The `images` hook is now `media`.** `media(output)` returns entries, not strings: `{ url }` to fetch a picture for the model, `{ url, sent: true }` to show it to the person too, or a reference `{ type, mimeType, uri }` that is shown and never fetched. Change `images: (o) => o.urls` to `media: (o) => o.urls.map((url) => ({ url }))`.
- **Image URLs in a tool's output no longer become media.** The page no longer finds image addresses in a tool's output and shows them. `collectPromotedMediaFromToolOutput`, `promotedMediaFromUrlString` and `PromotedToolMedia` are gone, and a `media` transcript block has no `url` or `previewUrl`. A tool block's media now holds `data` or a reference `uri`, and `fromTool` and `sent` say where it came from. A stored transcript whose `media` block holds `url` no longer parses. The direct-run panel no longer shows the image links in a call's output either: `layoutResult` returns no `images`, and `returnedMedia` takes only the call's parts. To show a picture, return it in `parts` with `sent: true`, or return a reference.
- **The chat shows only the tool media a tool sent.** Before, `TheoremChat` showed every media part of a tool's `parts`. Now, by default (`media="sent"`), it shows only the parts marked `sent: true` and the references. Mark the parts the person should see with `sent: true`, or pass `media="all"` to show every part.
- **The MCP handler sends only what a model reads.** `tools/call` on a `createTheoremMcpHandler` handler returns the text and media a model reads. It leaves out the references a tool returned, and all the media of a hidden tool, whose `complete` event now says `hidden: true`.
